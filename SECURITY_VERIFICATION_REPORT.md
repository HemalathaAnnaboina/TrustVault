## 1. Executive Summary

This report documents the evidence-based security threat verification conducted on the **TrustVault** backend codebase. Every documented threat from `THREATS.md` and key enterprise threat vectors—including **project membership boundaries versus document-level granular permissions**, cross-client multi-tenant isolation, cross-project isolation, revoked grants, dynamic expiry, malicious uploads, audit log tamper detection, and unauthorized role escalation—were systematically inspected against actual backend source implementations and tested with automated JUnit regression tests.

All automated attack simulation tests were compiled and executed against the live Spring application context using the Maven wrapper (`mvn test`). Every simulation verified that the system accurately enforces the defense-in-depth security model and returns expected HTTP status codes (HTTP 401 Unauthorized, HTTP 403 Forbidden, HTTP 400 Bad Request, HTTP 429 Too Many Requests) and immutable audit log records.

## 3. In-Depth Analysis: Project Membership vs. Document-Level Granular Permissions

A critical requirement of the TrustVault security model is the separation between **Project Membership** and **Document-Level Permissions**:

### The Architecture:
1. **Project Membership**:
   - Allows a user to view project metadata and see the list of documents that belong to the project.
   - For all documents where the member lacks an explicit `DocumentPermission` grant (and is not the document owner), `DocumentService.mapToDto` sets:
     - `userAccessLevel = "NONE"`
     - `canRead = false`
     - `canEdit = false`
2. **Document-Level Permissions (`READ` / `EDIT`)**:
   - `DocumentAuthorizationService.requireReadAccess()`: Requires explicit active grant (`READ` or `EDIT`) or ownership. Without it, throws `ForbiddenException` (HTTP 403 Forbidden).
   - `DocumentAuthorizationService.requireDownloadAccess()`: Requires `EDIT` grant or explicit download permission. `READ`-only viewers are denied with HTTP 403 Forbidden.
   - `DocumentAuthorizationService.requireEditAccess()`: Requires `EDIT` grant. `READ`-only viewers or users with `NONE` are denied with HTTP 403 Forbidden.
   - `DocumentAuthorizationService.requireManagementAccess()`: Requires document ownership, project manager role, or `ROLE_ADMIN`. Project members (even with `EDIT` grant) cannot delete documents or manage permissions.

### Automated Test Verification Evidence:
In `TrustVaultProjectDocumentSecurityTests`:
- `test01_memberSeesSafeMetadataWithNoAccessAndDirectActionsForbidden`:
  - Sita is an active member of `alphaProject` containing 3 documents.
  - Listing project documents returns all 3 documents with safe metadata, and all show `userAccessLevel = "NONE"`, `canRead = false`, `canEdit = false`.
  - Direct API requests to bypass UI controls:
    - Direct Preview (`GET /api/documents/{id}/preview`): **HTTP 403 Forbidden**
    - Direct Download Token (`POST /api/documents/{id}/download-token`): **HTTP 403 Forbidden**
    - Direct Edit (`PUT /api/documents/{id}`): **HTTP 403 Forbidden**
    - Direct Delete (`DELETE /api/documents/{id}`): **HTTP 403 Forbidden**
- `test02_grantReadToOneDocumentAllowsOnlyThatDocumentPreview`:
  - Manager grants `READ` on Document 1.
  - Document 1 now shows `userAccessLevel = "READ"`, `canRead = true`, `canEdit = false`.
  - Document 2 and Document 3 remain `userAccessLevel = "NONE"`, `canRead = false`.
  - Member can preview Document 1 (**HTTP 200 OK**).
  - Member attempting to download Document 1 receives **HTTP 403 Forbidden**.
  - Member attempting to edit Document 1 receives **HTTP 403 Forbidden**.
  - Member attempting to delete Document 1 receives **HTTP 403 Forbidden**.
  - Direct preview of Document 2 and 3 remains **HTTP 403 Forbidden**.

## 5. Security Recommendations for Production Deployment

1. **Active Rate Limiter Store**: In multi-instance or Kubernetes cluster deployments, replace the in-memory `ConcurrentHashMap` inside `RateLimitingFilter` with a distributed Redis-backed rate limiter or API Gateway rate-limiting rule (10 requests/minute/IP on `/api/auth/login`).
2. **Database Permissions**: In the production PostgreSQL database, revoke `UPDATE` and `DELETE` privileges on the `tv_audit_logs` table for the application database role. This provides database-level immutability in addition to application-level hash chaining.
3. **Vault Storage Encryption**: Enable AES-256-GCM server-side KMS encryption for cloud storage (AWS S3 or Google Cloud Storage) and block all public bucket access.
4. **HSTS Header**: Ensure TLS termination at the reverse proxy (Nginx/Cloudflare/AWS ALB) includes `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`.
